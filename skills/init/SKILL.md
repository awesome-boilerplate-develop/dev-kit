# init

**Harness.** Written for Claude Code, which replaces the plugin-root variable below with the dev-kit folder. If you see `${CLAUDE_PLUGIN_ROOT}` literally, your harness did not replace it: the dev-kit folder is two levels above this SKILL.md after resolving symlinks (the folder that contains `rules/RULES.md`). Read every `${CLAUDE_PLUGIN_ROOT}/…` below as a path in that folder, and first read `harness/<your harness>.md` there (`codex`, `copilot`, `opencode`, `antigravity`, `omp`): it maps `dk:<skill>`, subagents and the review agents to your tools.

Prepare, never run controller logic. Re-running only checks and fills gaps; never overwrite existing files. dev-kit is personal (rule O1): nothing it creates is committed, and it never edits a tracked file.

**Parts of a run.** `dk:init` runs everything below. `dk:init index` runs step 5 only (for example in a new worktree), `dk:init baseline` step 6 (the known-failure list may only shrink), `dk:init standards [rules|review]` step 7 (both passes, or the one named), asking the quick-or-detailed question of step 5 first.

**How to ask: probe first, then one question at a time, in order.** Before each question, find out what you can from the code, the graph and the files, and show that evidence with the question. Ask **one question per message**, in the order of the steps below, each with a default and short options, and wait for the answer before moving on. Number them ("Question 3 — commands"). "default" and "skip" are always valid answers. Never ask what the code already answers, and never batch questions. Ask only the questions the steps name: never ask permission to run a step or to continue (the baseline runs without asking; after an answer, go straight to the next step). If nobody can answer (headless run), take the defaults and list them as assumptions in the report.

**Every question ends with choices plus Other.** After the evidence, list lettered choices, at most 4:
- `A` is the recommended answer, marked "(Recommended)" and spelled out in full, so the user sees exactly what it does (for example "A. (Recommended) base `master-p2b`, test `npm run test-headless`, build `npm run build`, no lint");
- `B`, `C`, `D` are the real alternatives (another branch, "skip", "stop"); no filler choices;
- the last line is always "Other: type your own answer" (a change, a value, item IDs, free text).

**A choice that names item IDs explains them.** Write what each ID is in a few words, in the label or its description, for the IDs kept and for the IDs switched off: "Keep U2 (block a write while one is in flight); off: U1 error messages, U3 loading and error states, U4 reset after a write, U5 labels and keyboard", never "Keep U2, turn off U1/U3/U4/U5". When the tool shows its question text, put the group's items there too, one per line (ID and a few words). The user must be able to choose from the form alone.

"default" or Enter means `A`. If your harness gives you a tool that asks the user with choices (Antigravity `ask_question`, Copilot `ask_user`, omp `ask`), use it with the same choices, `A` first with its "(Recommended)" label; add "Other" as a choice only if the tool does not offer free text itself. If the tool comes back skipped or empty (a headless run auto-skips it), nobody can answer: take `A` and list it as an assumption, as for any headless run; do not ask the same question again. Without such a tool, write the choices as text. Never end a question with only "type default or a value".

**The tool is only the last line of the question, never the whole question.** Before calling it, write a normal reply the user can read on screen with everything the step asks you to show: the evidence, the group's list in detail (every item: what it asks, why, where this repo hits it, with counts), the drafted items of a read-back, the explanation the `CONSTRAINTS.md` step requires, and the "how it fits this repo" part of a confirmation. A choice label is a short summary of that reply, not a replacement for it. Your reasoning does not count as a reply: text that appears only in a thinking block or a tool log is not seen by the user (in one run the agent wrote the evaluation of three kit groups in a row only as reasoning, and the user saw forms like "Keep U2, turn off U1/U3/U4/U5" with no idea what those IDs were). This holds for every group of a run, the last as much as the first.

## Machine (skipped when already done)

1. **Graph tools.** Run `bash ${CLAUDE_PLUGIN_ROOT}/scripts/install-graph-tools.sh --check`. Only if a tool is missing, **ask** whether to install it (default: yes). On yes, run `bash ${CLAUDE_PLUGIN_ROOT}/scripts/install-graph-tools.sh --install` (pinned versions; tools already present are left alone) and use the absolute path it prints if the tool is not on PATH. On no, continue and note "rule G1 off: <tool> not installed". Never run `codegraph install` or `code-review-graph install`: they register MCP servers, hooks and instruction files.
2. **Personal settings.** None for now: dev-kit is set up one repo at a time, and every standard `dk:init` writes belongs to this repo. Standards shared across repos (`standards.team`) are not offered yet; a path the user sets there by hand is still loaded by the controllers.

## Repo

3. **Probe, no questions.** Record `git status --porcelain`. Detect the test/lint/build commands (`Makefile`, `package.json`, `pyproject.toml`, …), the stack, the linters and type checkers with their configs (what they already enforce), files the repo already tracks under `.dev-kit/`, and the project's own `GLOSSARY.md`, `docs/adr/`, `CONSTRAINTS.md`. List the enabled plugins and remind the user to invoke `dk:<controller>` by name.
   - **Base branch:** `origin/HEAD` alone is not enough (it can point at a branch nobody merges into any more). Compare it with the remote branch that recent pull requests merge into (the newest merge commits, such as "Merged PR …", across `refs/remotes`) and with the current branch's upstream; for each candidate note its last commit date and how many commits it is ahead of the others. If they agree, propose that branch; if not, step 4 asks it as a choice with that evidence.
4. **Question: commands and base branch.** Show what you detected; the user confirms or corrects. Then create `.dev-kit/` with `specs/`, `plans/`, `reports/`, and `.dev-kit/.gitignore` containing `*` (git ignores the whole folder; do not touch the repo's `.gitignore`; `sdd/` comes later), and write `.dev-kit/config.yml` from `${CLAUDE_PLUGIN_ROOT}/templates/config.yml`.
5. **Question: graph indexes** (default: yes). State the expected size from the number of code files the tools will index: count source code only (`.ts`, `.js`, `.py`, `.cs`, `.go`, `.java`, … tracked by git), not templates, styles, assets or dependencies; about 0.16 MB per file for codegraph and 0.6 MB per file for code-review-graph (measured: 136 MB and 529 MB for ~850 indexed files, in a repo with ~1,450 files under `src/`). On yes, run `codegraph init` and `code-review-graph build`, then fix `git status` in this step, not later: the repo's exclude file is `git rev-parse --path-format=absolute --git-path info/exclude` (in a worktree `.git` is a file, and the exclude file is shared by every worktree of the repo); append to it each index folder that `git status --porcelain` now lists (codegraph keeps its own `.gitignore` visible, so `?? .codegraph/` appears and `.codegraph/` must be added), never `.dev-kit/` (its own `.gitignore` already hides it), and never a line that is already there; then check `git status --porcelain` is back to what step 3 recorded. Set `graph.codegraph` / `graph.crg` in `config.yml`. Build the index before step 7: the standards probe uses it.
   - **Question: quick or detailed setup** for the standards (step 7) and `CONSTRAINTS.md` (step 8), asked right after the indexes, in a full run and at the start of `dk:init standards`; not in `dk:init index`. Choices: `A` quick (Recommended): the agent probes and drafts every group as in detailed mode, takes each Recommended line itself, and asks once, with one read-back of everything it will write (see "Quick setup" in step 7); `B` detailed: one question per group, with the loops for the user's own conventions; Other. The baseline question of step 6 is still asked when the tests are red, in both modes: stopping to fix tests is the user's call.
6. **Baseline.** Run the test and build commands once, writing their output to `.dev-kit/baseline-test.log` and `.dev-kit/baseline-build.log` (never a shared folder such as `/tmp`); take counts, failing groups and failing test names from those files, never by running the suite again. Green → record it. Red → report the counts and main failing groups, then **ask**: stop (fix the baseline first) or accept the current failures as known. If accepted, write `.dev-kit/baseline.md` from `${CLAUDE_PLUGIN_ROOT}/templates/baseline.md`: date, commit, command, totals, and the failing test names, one per line, exactly as the runner prints them. Never fix or skip tests here. **Tests could not run** (restore, authentication, missing service or toolchain) is not a red baseline: report the error and **ask**: stop and fix the environment, or continue with the baseline marked "not measured" in `config.yml` and the report (controllers then treat every test failure as new until `dk:init baseline` succeeds).
7. **Standards by topic** (below).
8. **Question: `CONSTRAINTS.md`** (optional, default: no), asked on its own after the standards are written, never folded into another question; in quick setup it is not asked (default no, said in the read-back). If the project has its own `CONSTRAINTS.md`, say that it will be read and skip the question. Otherwise the question must explain itself, in the user's language, filled in with what step 3 found:
   - **What it is:** a written quality bar for *how good a change must be before it ships*, as numbers, each with the command that checks it (for example "zero type errors: `tsc --noEmit`", "changed lines ≥ 80% covered", "no high security findings: `semgrep`"), plus a floor that always applies (no new suppressions such as `@ts-ignore`, no stubs, no skipped or deleted tests, no secrets) and a list of agreed exceptions.
   - **How it differs from the standards just chosen:** standards say *how code in this repo is written* (rules the agent cannot guess, used while coding and reviewing); `CONSTRAINTS.md` sets the *pass bar and the tools that measure it*, and exists so the agent cannot quietly lower the bar to get green.
   - **What the user already has without it:** `dk:pre-pr-check` already flags new skips, suppressions, deleted asserts and weakened thresholds in the diff; list the checks the repo already runs (type checker, linter, coverage, CI gates) from step 3.
   - **What it would add here:** the dimensions that are missing from that list (for example "no linter and no coverage gate today").
   - **Cost:** up to 4 more questions (which dimensions, block or warn, target numbers or "measure today and hold", slowest acceptable check); possibly installing a tool, always asked first; its benefit has not been measured in the dev-kit lab.
   - **Where and who reads it:** `.dev-kit/CONSTRAINTS.md`, personal and never committed; `dk:pre-pr-check` step 1 reads it, and a change that breaks it is a blocker.
   - **Answer:** "no" (default; nothing is lost, the floor checks above still run) or "yes".

   On yes: write `.dev-kit/CONSTRAINTS.md` via part `constraint-driven-development` (`${CLAUDE_PLUGIN_ROOT}/parts/`), keeping its one-question-at-a-time interview.
9. **Report.** Write `.dev-kit/init-report.md`: found, created, missing, the answers and assumptions, the standards enabled, commands run with output. Compare `git status --porcelain` with step 3: it must be unchanged; fix anything new by adding it to the exclude file from step 5 (never `.gitignore`), or report it. Say a line was added to the exclude file only if you ran the command that added it in this run, and quote that command.

## Step 7: standards in two passes

Rules are written only for what the agent **cannot know by itself** or has been seen to get wrong (principle 0, `docs/en/09-init-and-standards.md`). Never ask about naming or style: the agent reads it from neighbouring code, and the linter checks the rest.

**Probe first, no questions, graph first.** When step 5 built the indexes (`graph.codegraph` / `graph.crg` true), find the structure with the graph before reading files (rule G1, `${CLAUDE_PLUGIN_ROOT}/rules/graph-playbook.md`); grep and file reads are for what the graph cannot answer. Run once, in this order:
1. Freshness: `codegraph sync` and `code-review-graph update -q`.
2. **Areas of the code:** `code-review-graph architecture --detail-level minimal`: the communities (name, size) and warnings are the starting list for the architecture group.
3. **Central pieces, by topic:** `codegraph explore "<topic>" --max-files 5` for each of: how the backend is called (HTTP or data access), permission or role checks, configuration and environment values, shared base classes or helpers, personal or medical data. Its "Blast radius" lines give symbols with caller counts (for example "`<permission key map>` — 93 callers"): use those counts as evidence. Follow one symbol with `codegraph callers <symbol>` or `codegraph node <symbol>`; these work on symbols defined in the repo, not on framework classes (`codegraph callers HttpClient` finds nothing).
4. **Then files and grep, only for what the graph does not hold:** what the linter and compiler already enforce (their configs; reviewers must not report it again); in-house libraries: internal-scope packages in `package.json` (old and new versions), how many files import each, template tag prefixes against framework controls (`mat-*` and similar), which one recent files use, and the component list from the package's `public-api.d.ts` / `index.d.ts`; what the repo exposes to others (public API, federated remotes, events) when the graph did not show it.

Without indexes, do steps 2–4 with files and grep. In `init-report.md`, list the graph commands you ran.

**How each question looks.** One **group** per question, like a brainstorm: one question per message, multiple choice where possible, wait for the answer.
- **The list in detail:** every item with its ID, what it asks of the code, why, and where this repo hits it (a count or a file from a command you ran). Say for each item whether it applies to this stack (the stack found in step 3: a web front end, a mobile app, a back-end service): a kit file is offered when its `applies_to` matches the repo, whatever the platform, so mark an item that does not fit (a server-side check in a client app) as "does not apply here" with the reason, and name the stack's equivalent of a platform term (`localStorage` is `AsyncStorage` in React Native). Mark each kit file `validated` or `experimental`. A claim such as "X replaces Y" needs usage evidence (recent files use X, or X is used more than Y); otherwise it becomes a choice (`A: shared/services` / `B: services`).
- **Recommended:** one line the user can accept as is, one reason per part from the probe. Recommend an `experimental` kit file when the probe found the situations its items cover; leave out items the linter or compiler already checks or nothing in the repo triggers (for example an item about server-side checks in a front-end repo); recommend a repo item only when usage shows a clear direction and no fact is still needed from the user; prefer a lint rule when a linter could enforce it. "All items" is a choice, not a default: recommend it only when the list above shows repo evidence for every item. The line is one decision, never "if I had to pick"; with nothing qualifying, write `Recommended: nothing` and why. Before sending, check the line against the text above it: every item the text recommends is in the line, and nothing else.
- **Answers:** "default" (`A`) accepts the Recommended line exactly as shown; "skip" takes nothing from the group; "Other" takes items one by one (letters or IDs, `<id>#<item>` to switch off one kit item) or free text. Never enable a file or keep an item that was not on the screen. Never ask whether an item is for the project or a team: everything kept belongs to this repo.
- **Confirm every item the user adds in their own words** (a convention, a review check, a Do-not-flag line), in any group or loop, before keeping it. Make it its own question, then continue where you were:
  - **How you understood it,** drafted as the item will be written: the trigger ("When X, …"), what it asks, where it applies (folders, kinds of file, new code only or existing code too), exceptions, the severity;
  - **How it fits this repo,** from commands you ran: how many places follow it today and how many do not, with one example of each; anything it conflicts with (a kept rule, a framework or library default, a neighbouring pattern such as a second base class); whether a linter, the compiler or a kept rule already covers it (name the config), or whether the agent already sees it in neighbouring code (principle 0); and whether a reviewer can check it at all: `dk:pre-pr-check` sees the diff, the spec and the graph summary, not the PR description, CI results or screenshots, so say so when the item depends on them;
  - **The question:** "Is this what you mean?" with choices: `A` yes, as drafted; `B` narrower (a concrete proposal, for example "new master tables only", or a version a reviewer can check from the diff); `C` wider (a concrete proposal); or a correction in their words. When the evidence shows no gap (it matches the code and nothing conflicts), say so in one line, and keep the choices.

  Keep the item only after the answer, under the ID shown in the confirmation (never renumber it when writing); on a correction, draft and confirm again.
- **Read-backs** are their own message and show what will be written: every drafted repo item in full (ID, trigger, what it asks, severity, file), the kit files kept and the items switched off. Never "as above" without the list. Nothing else is asked in it (not the next group, not `CONSTRAINTS.md`). Wait for the answer and write only after a yes. Never decide an answer for the user: no reply is not a "no".
- Skip a group with nothing to show. Number the questions ("Question 9 — rules: coding").

### Pass 1: rules for writing code (`## Design`, `## Implement`)

Used by `dk:story-runner`, `dk:bug-fixer` and `dk:code-refactor` while writing code. Groups, in order:
1. **Architecture**, from the probe: the kit has no architecture file (principle 0: it depends on the repo), so the probe is the standard list. Present the structure as items to confirm: layers and where new code goes, how data is reached, the module system, exposed contracts, config and environment values, permission keys. Each item is a candidate rule with its evidence. Keep out of Recommended what an agent sees by reading neighbouring code (where an existing kind of file already lives, a pattern every file follows); recommend placement only when two places compete or recent files moved.
2. **One group per kit file** with `## Design` or `## Implement` items whose `applies_to` matches the repo: `coding/review-basics`, `testing/basics`, `security/basics`, `ui/forms-and-actions`. Show the items of those sections only. **Not offered when the trigger is absent:** before listing a file's items, look for each item's trigger (its "When …" condition) in the repo with a command (graph or grep), for example server handlers for a server-side check, HTML, URL or WebView sinks and shell or query calls for an injection check, a test runner for the testing items. An item whose trigger a command shows to be absent is not a row and not part of Recommended: list it in one line under the table, "Not offered, no trigger in this repo: S1 (no server handler: `<command>`, 0 files), …", and it goes to `standards.disable` if the file is kept. Keep an item as a row when its trigger needs reading code (what an error message shows, what is stored where, whether a secret ships) or the command is not conclusive: a grep finding nothing is not proof there. The user brings a not-offered item back through Other. A kit file with no offered item is skipped with that one line.
3. **In-house libraries**, one group each: draft the rule from the probe (Implement, Review, Do not flag, with the component list) and ask only what the code cannot show: is the old version still allowed in new code, and which framework controls stay allowed (the `Do not flag` exceptions).
4. **Your own conventions (loop):** list the other repo suggestions the probe supports, each with its evidence, as choices, plus free text. Ask again after every answer, "default" included (it takes the Recommended line), until "no" or "skip". Never ask a bare "anything else?"; build each loop question from the context, in the user's language:
   - one line on what was just added (or "nothing added");
   - what the kept rules cover so far, by area, in a few words;
   - at most 3 new areas of this repo that no kept rule touches yet, each with its evidence from the probe (a folder, a dependency, a flow with its file count); areas offered before are listed by letter only;
   - **one question sentence** that names those areas, for example: "Rules so far cover permission keys, environment values and translations; nothing yet on date handling (`<date library>` in N files) or the report screens (N files under `<folder>`). Is there a convention there, or anywhere else, the agent should follow when writing code?";
   - how to end ("no"). Any claim that a linter or the compiler already covers something names the config that shows it.

   When the probe has no uncovered area left, say so and ask once whether the team has a convention the code does not show.

Then **read the pass-1 rules back** (drafted repo rules and kit choices) as their own question; write only after the user confirms.

### Pass 2: review checklist (`## Review`, `## Do not flag`, `## Severity`)

Used by `dk:pre-pr-check` and its reviewers. Do not ask again about items kept in pass 1: each one is checked in review at its severity. Open with one line saying so, and that `review/finding-quality` (the finding gate, R1–R7 and the certain/suspect tiers) is always on. Groups, in order:
1. **Severity:** a table of the rules kept in pass 1, each with its severity (kit items show theirs; propose one for each repo rule from the probe: blocker when data is written wrongly or a contract breaks, major when a user sees wrong behavior, minor otherwise). The user may change a repo rule's severity; a kit item's severity changes only through a project rule that overrides it (`docs/en/09-init-and-standards.md` 9.3).
2. **Review-only checks:** what a reviewer checks that is not a rule for writing code, found in the probe as "when the diff touches X, check Y", for example: version pins that must match another file, generated or vendored files that must not be hand-edited, a migration that needs a rollback, a changed public contract whose consumers must be told. Leave out any check that restates a rule kept in pass 1 (an environment value in every file, a translation key in every language): that rule is already checked. Show each with the file count or path.
3. **Do not flag:** what the linter, compiler and CI already enforce (from the probe), the `## Do not flag` lines of the enabled kit files, and repo patterns that would only be noise (for example a legacy folder the team does not touch). The user adds or removes items.
4. **Your own checks (loop):** as in pass 1, built from the context, never a bare "anything else?": what reviewers will now check, by area; 2–3 kinds of change the checklist does not cover yet, with evidence (for example "changes under `<folder>`, N files; to the pipeline files"); then ask whether reviewers should check something there, or leave something alone. Ask again after every answer, "default" included; only "no" or "skip" ends the loop.

Then **read the pass-2 checklist back** as its own question; write only after the user confirms.

There is no question limit; the loops end when the user says no. In a headless run, take each Recommended line, end the loops at once, and list the choices as assumptions in the report.

**Quick setup** (the user chose `A` after step 5). Probe and draft every group of both passes exactly as above (lists, evidence, the not-offered line, Recommended), but do not ask per group: take each group's Recommended line, run no loop for the user's own conventions or checks, and do not ask `CONSTRAINTS.md` (default: no). Then send **one read-back** as its own reply, written as a **checklist with the Recommended items already ticked**: one line per item, `☑` for an item that will be written or kept and `☐` for one that will not (switched off, not offered, or drafted but not recommended), each with its ID, a few words on what it is and the reason in a few words. Not-offered items get their own `☐` lines too, with the command and count as the reason, so that every ID the user may tick is on the list. Group it by kit file, then the drafted repo rules (with trigger, severity and file), the review-only checks and the Do-not-flag lines, each with the file it goes to, so that no file is chosen after the approval; end with "`CONSTRAINTS.md`: not created (a detailed run asks for it)". Ask once: `A` write as ticked (Recommended); `B` change the ticks with forms; `C` go through it group by group (switch to detailed); `D` stop without writing; Other: changes as `+ID` to tick and `-ID` to untick (for example `-S5 +S1`), or new items in your own words. IDs are unique only within a file, so where an ID appears in more than one file of the checklist (repo checks are often all `V1`), print the file on those lines and take the change as `file#ID` (`-ops/environment#V1`), the form `standards.disable` uses; ask back when a bare ID matches more than one line.

For `B`, ask one multiple-choice question per kit file, then one for the repo rules and checks, listing every item of that group with its current state as a word at the start of the label (`on · S4 secrets out of source and builds`, `off · S1 server-side record access`, in the user's language), not as ☑/☐, because the form draws its own checkboxes; an item whose ID repeats in another file shows its file; last comes a `Keep this group as shown` option, marked Recommended, because a form sent with nothing ticked is not a clear answer (omp's RPC clients show a Done row only after a tick) and omp picks the Recommended option when a question times out, so a timeout changes nothing. The question says: "Tick the items to switch: on becomes off, off becomes on; to change nothing, tick only Keep this group as shown." A tick means a switch, not the final state, because the CLIs' choice tools cannot pre-tick options; without a multiple-choice tool, ask for `+ID`/`-ID` as text instead. A new item in the user's words is confirmed like any user-added item. After any change, show the lines whose mark changed, with their new marks, and ask `A` write / Other once more. Write only after `A`. In `init-report.md`, record that quick setup was used, the Recommended lines taken and every mark the user changed.

**Write, after each read-back.**
- Turn kept items and free-text answers into items in `${CLAUDE_PLUGIN_ROOT}/templates/standard.md` format: one idea per item with an ID, a trigger ("When X, …"), a one-line why and a severity. Say so when an answer breaks principle 0 (the agent already knows it, or a linter checks it) and suggest not writing it.
- **IDs:** decide the topic file of an item when you first show it, and take its ID from that topic: one letter and a number, unique in the file, never changed afterwards. Rules (`## Design`, `## Implement`) use the topic's letter: `A` architecture, `C` coding, `T` testing, `S` security, `U` ui (in-house component libraries included), `P` api, `D` data, `O` ops, `R` process. A review-only check uses `V`. `## Do not flag` lines need no ID. A date-handling convention is coding (`C`), not data; data means stored data, schemas and migrations.
- **Where items go:** pass-1 items under `## Design` or `## Implement` of the topic file the rule is about; pass-2 items under `## Review`, `## Do not flag` and `## Severity` of the topic file of what they check: environment, pipeline, deployment and dependency files go to `ops/`, translation files to `ui/`, exposed module contracts to `architecture/`. Create that topic's file if needed; never put a check into a file only because it is open.
- Repo items → `.dev-kit/standards/<topic>/<name>.md`, with `id: <topic>/<name>` matching the path, `status: experimental` as in the template (a repo rule is not measured yet), and the file `id` and item IDs exactly as shown in the read-back. Kit files kept in either pass → `standards.kit`; switched-off kit items → `standards.disable`.
- **Check what you wrote:** from the repo root run `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/check_standards.py`. It checks the frontmatter (`id` matches the path, `topic`, `scope`, `status`), that every `applies_to` glob matches a tracked file, the section names (each at most once), and the IDs (format, unique, every ID a Review line names is defined). If it prints FAIL lines, fix the files and run it again (at most 3 times); if it still fails, say so in the report. Put its last output in `init-report.md`.
